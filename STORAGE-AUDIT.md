# Storage responsiveness and memory audit — 2026-10-01

Scope: SPI SD, VIEWE SDMMC, web file transfer/listing/indexing, audio file/overlay loading, Save Data and plot history. This is a source audit and remediation record, not a claim that physical card latency, watchdog behavior or sustained throughput has been measured.

## Changes

| Path | Finding and remediation |
| --- | --- |
| SD maintenance | Hotplug/retry probing previously ran from the main loop. It now runs in a low-priority maintenance task. Configuration changes wait for active leases; mount admission checks read/write counters atomically and no longer resets them underneath clients. Failed mount backoff remains bounded and failure counting saturates. Initial boot mount and explicit remount remain synchronous. |
| Space reporting | Ending every write could scan FAT free clusters, including after each recorded sample. Writers now mark the cached summary dirty; idle maintenance refreshes at most every 30 seconds. Displayed free space is cached, not an allocation guarantee; short writes remain errors. |
| Downloads | Network callbacks previously read the card directly, shared one mutable transfer buffer and could leak a read lease on disconnect. Each response now has a background producer, private 4 KiB ring and non-waiting consumer. Limit two streams; yield between 1 KiB reads, cancel abandoned responses and stop a reader stalled behind a full buffer for 30 seconds. File length is advertised so a short transfer is not a successful complete download. |
| Uploads | Guard shared state with one owning HTTP request. Reject competing/multiple-file uploads and busy SD uploads. Track whether the destination was actually opened before removing an incomplete file. Disconnect/error releases the write lease. Transfer copying uses a bounded 4 KiB buffer; schedule directory reindexing through the existing worker. Card writes/flush inside upload callbacks are still synchronous. |
| Directory operations | Bound index-line parsing so a corrupt line cannot grow a card-sized String. Clamp page size to 1–128 entries and stop scanning after the page, rather than scanning the whole tail just to count it. Paged totals are lower bounds while more entries exist; explicit count remains exact. Reindex requests use the existing background job. Delete rejects busy SD, holds a lease and bounds recursion depth to eight. Exact counts, traversal to a large offset, and recursive deletion still perform synchronous filesystem work. |
| Recording | Queue payload prefers PSRAM. Drain up to eight consecutive samples for the same file under one open/flush/close cycle and yield between batches. Keep bounded queue admission and explicit write/full-queue errors. A queued sample is not a durable write acknowledgement. |
| Plot history | Replace byte-at-a-time card reads with 512-byte read-ahead, preserving logical byte offsets. Retain page/scan/time bounds and partial-line handling; pages hold at most 64 samples with PSRAM or 16 without. HTTP submits/collects one bounded history job; the worker accesses the card. `{pending:true}` instructs clients to retry the identical request. The browser polls every 100 ms with a bounded wait; uncollected completed jobs expire after three seconds. No HTTP request pointer is kept by the worker. |
| WAV overlay | The old loader allocated a file-supplied `fmt` chunk and a whole raw clip in addition to the decoded output. Read only the fixed 16-byte PCM format, validate chunk extents and output size, cap header parsing at 256 chunks, use stack header/chunk buffers, and convert in 512-byte blocks. Reject clips exceeding 1,048,576 stereo output frames. Decode buffer prefers PSRAM; internal fallback is capped at 32 KiB. Loading remains synchronous, with yields between conversion blocks. |
| Plot snapshots/JSON | Telemetry snapshots and recording/history JSON allocations prefer PSRAM instead of consuming large transient SRAM blocks. Allocation/JSON overflow becomes an explicit error. The small critical-section-protected live ring remains internal. |

## Memory policy

`include/storage_memory.h` allocates CPU bulk buffers in PSRAM first. Fallback uses explicitly internal 8-bit memory, a per-allocation bound (normally 8 KiB) and a 32 KiB free-internal-memory reserve check. This is admission control, not reserved memory: concurrent Wi-Fi/audio allocations can change available heap after the check. JSON growth and snapshot allocation can fail safely instead of assuming memory is available.

DMA buffers remain under the driver and task stacks/RTOS control structures remain internal. Do not move them to PSRAM indiscriminately. Downloads, recording and history add internal task-stack overhead even when their data buffers use PSRAM. Source changes must still pass the project's final image-capacity checks.

## Remaining synchronous boundaries and hardware acceptance

The Arduino SD/SDMMC/FatFS APIs are synchronous. Moving bulk work to tasks frees the main/network loop on those paths; it does not impose a hard deadline on a card driver call or cancel a wedged driver. This change therefore does **not** certify that all storage APIs are non-blocking or that reboots are impossible. Upload writes, initial/manual mount, exact directory counts, deletion and overlay startup still need a broader job/state-machine API if strict end-to-end non-blocking behavior is required. A failed card, unstable power, incorrect pin assignment or bus timing remains a hardware concern.

Before declaring release readiness, test on one PSRAM board (including VIEWE SDMMC) and one non-PSRAM board: concurrent playback/recording/download; aborted and competing uploads/downloads; removed/full/corrupt card; corrupt WAV chunk lengths; invalid/truncated JSONL; low-memory allocation failure; slow/disconnected clients; mount/reconfiguration during reads; sustained logging with heap, minimum internal heap, largest free block, PSRAM use, task stack high-water marks and watchdog/reset reason. Compare uploaded/downloaded hashes and recorded sample counts. Measure response latency and lost samples, not merely successful startup.

Validation in this turn: changed C3 sources checked with the actual compiler in syntax-only mode, S3 SDMMC branch checked separately, and the real browser plot-history test covers pending-job polling and existing paging/error/range/realtime behavior. No full firmware link, flash or physical SD/PSRAM stress test was performed. The bundled device-web assets were refreshed for the new history response behavior.

Android must port the worker/lifetime/memory behavior together with shared firmware and the `{pending:true}` history protocol. See the [Android parity handoff](../ELMA-IoT-Windows-main/WINDOWS-ANDROID-PARITY.md).
